# SUSP.OS — Slider Reference

Every slider in the app: its range, which tier exposes it, what it does
physically, and its effect on handling balance (oversteer/understeer).

Balance direction is sourced from the authoritative `bXxx` contributor
formulas in `index.html` (`bSp`, `bAb`, `bDampBias`, `bDiffAccel/Decel/
Front/Rear`, `bBrakeEntry`), not slider hint text alone — hint text has been
wrong relative to the actual formula twice now: Damping Bias (which said the
opposite of what `bDampBias` computes) and the FWD EXIT hint (which had the
lock direction backwards). Both are in [HISTORY.md](HISTORY.md). Every slider's
hint is quoted word for word in [HINTS.md](HINTS.md).

Convention across the app: **right = OVERSTEER, left = UNDERSTEER** for
every balance-relevant slider.

Every slider's value can also be typed: each one carries a number box beside
its label, the same box CHASSIS uses, and any derived text (FIRM, the resulting
bump ζ, F 0.25s | 0.28s R, Accel 26%) sits to its left. The box holds the
slider's own number, so on the flipped sliders (Damping Bias, EXIT, ENTRY) a negative number is toward
the left end. Two exceptions take the stored value instead: Target Speed's box
is the speed in mph or km/h though the slider runs inverted, and POWER SPLIT's is
the rear % (20–90) though the slider is centred on 50. A typed value is clamped to the
ranges below but not snapped to the slider's step.

**Measured values are number boxes, not sliders.** Where a control stands for a
real quantity you read off the car or type into the game (Weight, Wheelbase,
Track Width, Ride Height, CG Height, Motion Ratios, ARB F/R in MAN, the MANUAL
diff locks and Center Split, MANUAL camber/toe/caster, and the calibration
fields apart from MEAS. NAT BAL), `Field` gets `noSlider` and shows only the
box. Paired F/R boxes (Track Width, Ride Height, Motion Ratio, ARB Motion
Ratio) also get `stacked`, which puts the box under its label. Everything
else keeps its slider: the BEG trio, Front Weight Bias, ARB
Bias/Stiffness/Share, Mech Balance Target, Balance Offset, the spring Hz
sliders, Bottom-Out g, Target Speed, every damper slider, EXIT/ENTRY/POWER
SPLIT, Nudge Strength, MEAS. NAT BAL and the DNA axes. The tables below still list ranges for both kinds.

> Keep this in sync with `index.html` whenever a slider's range, mechanism,
> or tier gating changes — see the note in `CLAUDE.md` about reviewing docs
> after major changes.

## Beginner (BEG) — always visible

| Slider | Range | Effect | Balance Direction |
|---|---|---|---|
| Ride Stiffness | 0.8–5.5 Hz, slider step 0.01, stored on a 0.001 Hz grid | Sets the spring frequency of whichever axle RIDE REF. anchors; the other derives via the active Hz mode. BEG has no RIDE REF. toggle, but the stored value persists from any prior INT/PRO session, so this is not always the front axle — the slider's own label follows it (`Ride Stiffness` / `Avg Stiffness` / `Rear Stiffness`) | None directly — magnitude only |
| Ride Stiffness — STIFFNESS mode (INT/PRO RIDE panel, only shown with RIDE HEIGHT → CG on) | HZ / BOTTOM G's | Toggle next to RIDE REF. that swaps what the slider sets. HZ is the slider above. BOTTOM G's re-scales the same slider to the vertical-g load factor at which the active RIDE REF. axle bottoms out (`rideHeight_mm·(2π·Hz)²/9810`, inverted to solve Hz from a target g) — same sag model as the SAG vs LOAD chart. Range is that formula evaluated at HZ_MIN/HZ_MAX for the active axle's ride height, so bounds vary per axle/chassis. Switching between the two modes carries the current value across — HZ→BOTTOM G's seeds `rideBottomG` from the g the car is already at, and BOTTOM G's writes `rideStiffness` as it goes, so neither direction moves the car. Both `fe.rideStiffMode` and the target `fe.rideBottomG` are real persisted fields (codec ids 63/64, `DEF_FE`) — the target actively re-solves Hz whenever the chassis it applies to changes (ride-height edits, or a build/share-code landing a different target on the current chassis), not just a display convenience. With RIDE REF. also set to SHARED, this unlocks a SHARED **Hz mode** option (alongside MULTIPLIER/MECH/FLAT RIDE) that solves front and rear Hz to bottom out at the same g instead of holding a fixed Hz ratio — read-only display, no extra slider. Leaving BOTTOM G's (or leaving SHARED ride ref) rehomes that Hz mode to MULTIPLIER pinned at the ratio the car is currently sitting at, rather than falling back to FLAT RIDE, so both axles' Hz survive the switch. The g slider steps by 0.01, and because `Hz ∝ √g` one step is worth as little as ~0.002 Hz at the stiff end — which is why `hzToRs` snaps to 0.001 Hz rather than the 0.01 the Hz slider itself steps by; see [PHYSICS.md](PHYSICS.md#the-0001-hz-grid). See [PHYSICS.md](PHYSICS.md#bottom-gs-stiffness-mode) for the resolve mechanism and the RIDE REF. invariant it preserves, and [PHYSICS.md](PHYSICS.md#rearsecondary-hz-modes) for the SHARED Hz mode's formula | Same as Ride Stiffness — both modes drive the same underlying Hz value |
| Balance | −50..+50 | Centre is WEIGHT's neutral — bars split by weight distribution, springs at the MULTIPLIER ratio already set. Off centre it nudges both: WEIGHT-mode ARB Bias (±20 points of bar split at the ends) and the rear/front Hz ratio (±4%), applied incrementally on top of whatever ratio is already set (e.g. a loaded preset's), not a reset | Right = OVERSTEER, Left = UNDERSTEER |
| Character | −50..+50 | Sets rebound ζ (`70 − v·0.5`, so it reaches only ζ 45–95%) and bump ratio (`56 + v·0.22`). A tune below ζ 45% — including three factory presets — reads pinned at AGILE; see [KNOWN_ISSUES.md](KNOWN_ISSUES.md) | None — damping feel (STABLE↔AGILE) |
| Layout | FWD/RWD/AWD | Drivetrain type; reshapes diff behavior and natural balance | Indirect — redefines "neutral" |
| Weight | 100–18,000 lb | Scales spring rates, damper forces, ARB stiffness | None directly |
| Front Weight Bias | 30–70% | Front axle weight fraction | Higher front % → naturally more understeer-prone |
| Build Type | Street/Track/Drift/Rally/Offroad/Drag | Shifts alignment, diff AUTO behavior, brake balance, recommended targets | Indirect (changes recommendations) |

## Intermediate (INT) — adds these

| Slider | Range | Effect | Balance Direction |
|---|---|---|---|
| <!--@range fe.arbBias-->ARB Bias | −50..+50 | Shifts front/rear ARB split (WEIGHT: from weight default; NEUTRAL: from the springs-cancelling point (CANCEL) or the springs' own F/R proportion (EQUAL ROLL); CHASSIS (PRO): from the car's natural mech balance). **Hidden when ARB Stiffness Mode is MAN** — MAN sets front/rear ARB directly and bypasses the budget/split solve, so the bias has nothing to act on (Balance Mode is hidden there for the same reason) | Right = OVERSTEER, Left = UNDERSTEER |
| <!--@range fe.arbBasicMan-->ARB Stiffness (Stiffness Mode BASIC) | 0–100% | Sets an overall ARB roll-stiffness budget directly (0%≈1 click, 100%≈this game mode's click limit, per axle at a neutral split) — unlike SHARE %, doesn't scale with spring rate. Balance Mode still splits it front/rear like AUTO/ROLL/SHARE. **Hidden in BEAMNG** — the range is defined entirely as a fraction of the click ceiling, so it has no meaning without one. Listed under PRO here until an audit checked the gating: the BASIC button carries a `!physMode` guard and no `uiMode` guard, so it is available from INT up, like the other Stiffness Modes. Switching in seeds this by inverting the budget formula against the ARB roll stiffness currently running (`100·((rsAbF+rsAbR)/C − 1)/(lim.arb−1)`, `C = arbScale·(tF²+tR²)`), so the bars land near where they already were rather than at the stored 50%. Approximate on purpose — `rsAbF/rsAbR` come back through click quantisation and any limit pinning, and the slider's 1% step is worth ~0.6 of a click | None directly — redistributes level only, Balance Mode/ARB Bias set direction |
| <!--@range fe.arbTargetRollMan-->Target Roll Angle (Stiffness Mode ROLL °) | 0.3–5.0° @ 1g, step 0.01 | Body roll the bars are solved to allow at 1g lateral. Low (≈0.5–1°) = stiff bars and flat cornering; high (≈3–5°) = soft bars that let the suspension articulate. The solver inverts the roll equation to hit it, so the achieved angle can fall short when springs alone already exceed the target or the bars hit their ceiling — the output card says so when that happens | None directly — sets total ARB level, Balance Mode/ARB Bias set direction |
| <!--@range fe.arbShareMan-->ARB Share (Stiffness Mode SHARE %) | 0–80% | Fraction of **total** roll stiffness supplied by the bars. 0% = springs carry all roll resistance; 20–30% is typical sport. Higher means stiffer bars relative to springs and more abrupt lateral load transfer. Unlike BASIC, this scales with spring rate — change Ride Stiffness and the bars follow | None directly — sets total ARB level, Balance Mode/ARB Bias set direction |
| ARB F / ARB R (Stiffness Mode MAN) | Forza: 1–`lim.arb` clicks (65 HORIZON / 40 MOTORSPORT). BEAMNG: 0–200000 N/m | Direct ARB values, bypasses budget/split entirely. The max tracks the game mode rather than being fixed at 65 — `computeTune` clamps to `lim.arb`, so a fixed ceiling let you type values MOTORSPORT would silently discard. In BEAMNG the field shows BeamNG's linear Anti-Roll Spring Rate, has no ceiling, and is **not** snapped to BeamNG's 1000 N/m increment — a typed value is taken verbatim, the same way Forza's MAN bypasses the 0.1-click rounding, while the solved (non-MAN) budget does snap. Always **stored** as roll stiffness: displayed via `k = 2·rs/track²`, and converted by `ARB_RS_SCALE·track²` in both directions when the game mode changes. Balance Mode is hidden while MAN is active | More rear-relative → OVERSTEER |
| Split Direction (WEIGHT/CHASSIS) | SAME / OPPOSITE | SAME tracks the reference balance directly (front-heavy → front-heavy ARB). OPPOSITE mirrors the split around 50/50 (front-heavy → rear-heavy ARB), so the bars counteract the reference instead of following it. ARB Bias still nudges from whichever baseline this picks. | Indirect — flips which side WEIGHT/CHASSIS lean toward by default |
| Neutral Method (NEUTRAL) | CANCEL / EQUAL ROLL | CANCEL (default) splits the bars against the springs so the balance bar returns to neutral. EQUAL ROLL splits the bars in the springs' own proportion (`rF = rsSpR/rsSp`), so each axle's ARB carries the same % of that axle's roll stiffness — the bars add stiffness without moving the springs' balance. Shown as ARB ROLL % F/R. |
| <!--@range fe.reboundZeta-->Rebound ζ | 10–200% | Rebound damping ratio, both axles. Zone text beside the box: none below 68%, `BUTTERWORTH` 68–72% (ζ≈70.7% is a *point*, so only its neighbourhood carries the name), `FIRM` above 72%, `⚠ OVERDAMPED` above 100%. Marker at 70% is labelled BWORTH. Switching in from SETTLE TIME seeds this from `physics.baseZeta` — the ζ the target time was already back-solving to — so the tune on screen doesn't jump | None — magnitude/feel |
| <!--@range fe.bumpRatio-->Bump Ratio | 10–100% | Bump damping as % of rebound; the text beside the box shows the resulting bump ζ with the same BUTTERWORTH/FIRM/OVERDAMPED zones as Rebound ζ. Feeds the DYNAMICS chart — trace shape, settle marker and neutral ring all respond to it. Deliberately absent from the RESPONSE bar and from `bDampBias`, see [PHYSICS.md](PHYSICS.md#response--transient-character-responsefactors). Switching in from INDEPENDENT seeds this as `100·physics.bumpZeta/physics.baseZeta` — the bump anchor expressed against the rebound anchor — the mirror of the seed the other direction already did. A CROSSED tune (bump above rebound) does move here, since RATIO tops out at 100% and cannot express it | None — feel only |
| <!--@range fe.landingPct-->Drop (BUMP MODE → LANDING) | 10–600 %, default 75, step 1 | A % of the RIDE REF. axle's ride height (SHARED: the average); the hint shows it as a length in the CHASSIS unit. Because the drop scales with ride height, ride height cancels out of the solve: bump ζ depends only on BOTTOM G's and this %. Solves the softest bump ζ (10–115%) that absorbs a drop of this height without bottoming, on the RIDE REF. axle's Hz and ride height; Damping Balance Mode then splits it front/rear like INDEPENDENT's anchor. The LANDING button is offered only with RIDE HEIGHT → CG on, like BOTTOM G's. The readout shows the resulting bump ζ, `FLOOR` when even 10% catches it, `⚠ MAX …%` (the biggest drop 115% catches) when even 115% doesn't, `⚠ SAG ≥ RIDE HT` when static sag already uses the ride height, and `⚠ CROSSED` as Bump ζ does. While LANDING is active the DAMPERS table adds a Catch row: the drop each axle's final bump ζ really absorbs, as a % of the same ride-reference height (lengths in its tooltip). Switching in seeds the drop that the current bump anchor already catches. A stored target, like `rideBottomG`: bump re-solves on whatever chassis it lands on. See [PHYSICS.md](PHYSICS.md#landing-bump-mode) | None — feel only |
| <!--@range fe.bumpZeta-->Bump ζ | 10–115% | Independent bump damping. This is an **anchor**, not a per-axle value — Damping Balance Mode splits it front/rear exactly as it splits the rebound anchor (see [PHYSICS.md](PHYSICS.md#the-bump-stroke-gets-the-same-split)), so the readout shows `F x% \| y% R` whenever the two diverge and a single figure when they don't. Same readout zones as Rebound ζ, plus `⚠ CROSSED` when **either** axle's bump exceeds **that axle's** rebound ζ (not the raw Rebound ζ slider, which is the wrong yardstick under SETTLE TIME and under any split). Switching in from BUMP RATIO seeds this from whichever axle the active Balance Mode anchors, so the tune on screen doesn't jump. Same reach as Bump Ratio — DYNAMICS yes, RESPONSE and `bDampBias` no | None — feel only |
| Damping Balance Mode | STANDARD / TIME SYNC / HYBRID / EQUAL FORCE | One row of four buttons, stored in `dampBalMode` (`standard`/`sync`/`hybrid`/`neutral`). TIME SYNC is stored as `sync`, EQUAL FORCE as `neutral`. HYBRID is the per-axle mean of the TIME SYNC and EQUAL FORCE solves. Independent of REBOUND MODE — REBOUND MODE only decides how the anchor ζ is obtained (typed under CHARACTER, back-solved from a target time under SETTLE TIME); this decides how that value becomes a front/rear split, under either REBOUND MODE. STANDARD biases the anchor directly by percentage (simplest, Hz-agnostic). TIME SYNC solves so front and rear finish settling at the same time (Hz-aware, ignores corner mass). EQUAL FORCE solves so both axles push the same actual damping force (Hz- **and** corner-mass-aware) — mirrors ARB Balance Mode's WEIGHT/NEUTRAL pattern. The four are peers: there is no separate "Sync Method" control, and HYBRID and EQUAL FORCE are not sub-modes of TIME SYNC. The Damping Bias slider below works in all four and never resets when you switch modes — only the formula interpreting it changes. All four split the **bump** stroke as well as rebound, under every BUMP MODE. Under SETTLE TIME, only the ride-reference axle is guaranteed to hit the target time exactly (TIME SYNC derives the other axle's ζ to match it too; STANDARD, EQUAL FORCE and HYBRID split differently, so the other axle's real settle time is whatever falls out of that split — shown honestly in the DAMPERS table, not forced equal). The table highlights the row the chosen mode equalises: STANDARD → Rebound ζ, TIME SYNC → Settle, EQUAL FORCE → Force, HYBRID → both. | Indirect — changes what the Damping Bias slider solves for, not its own direction |
| Damping Bias | −50..+50 | STANDARD: the ride-reference axle holds the anchor and the other axle swings up to 50% — firmer one way, softer the other (under RIDE REF. SHARED both axles take half the swing). TIME SYNC: skews the equal-settle-time split (2× at ±50). EQUAL FORCE: skews the equal-force split (2× at ±50). HYBRID: skews the mean of the two. No readout — the DAMPERS table below shows settle and force per axle in every mode. Anchor is Rebound ζ under CHARACTER, the Settle Target-derived value under SETTLE TIME — same three Balance Mode formulas either way. | Right (REAR bias) = OVERSTEER, Left (FRONT bias) = UNDERSTEER |
| <!--@range fe.settleTarget-->Settle Target | 0.10–1.50s | Target settle time; back-solves rebound ζ (clamped 10–100%; markers at 0.35/0.60/0.90/1.30s = PLANTED/RACE/SPORT/ROAD, softer still is SOFT). Targets the `settleTimeFromZeta` envelope — the figure the DAMPERS rows quote, blind to bump damping — **not** the DYNAMICS chart's trace measurement, which can read differently. The 100% clamp is self-consistent with that envelope rather than physically optimal; see [PHYSICS.md](PHYSICS.md). Switching in from CHARACTER seeds this with `settleTimeFromZeta(physics.baseZeta, refHz)` on the ride-reference axle — the time the typed ζ was already producing — clamped to 0.10–1.50s, so the tune on screen doesn't jump. The round trip is exact while ζ≤100%; above it, coming back lands on the underdamped twin, since a settle time alone cannot distinguish the two roots (`rateToZeta`) | None directly |
| <!--@range fe.rearHzMult-->Rear/Front Multiplier | 0.50–3.00× | Secondary axle Hz as ratio of anchor | Higher → OVERSTEER-leaning, lower → UNDERSTEER-leaning |
| Independent Hz | 0.8–5.5 Hz | Manual secondary-axle Hz | Stiffer axle resists roll more there |
| CG Height Source (CHASSIS) | RIDE HEIGHT / MANUAL toggle, defaults to RIDE HEIGHT | RIDE HEIGHT estimates `ch.cgHeight` from Ride Height F/R + tyre radius (see next row); MANUAL exposes the CG Height field directly | None directly — feeds `ch.cgHeight` |
| CG Height (MANUAL) | 200–1500mm | Roll moment arm | None directly |
| Tyre Size F/R (CHASSIS) | e.g. `265/35R18` | Diameter/radius feed the RIDE HEIGHT CG estimate, AWD AVG RADIUS and the recommended CENTER SPLIT; width is grip capacity, and an asymmetry nudges displayed Mech Balance. Moved down from PRO: INT's default CG source already depended on it | Wider rear → less oversteer; wider front → less understeer |
| Ride Height F/R (RIDE HEIGHT) | 0.5–48in / 1.3–122cm | Estimates CG height from ride height (as shown on Forza's stat screen) + tyre radius — tyre radius comes from Tyre Size F/R (next row). Also drives a SAG vs LOAD chart (static sag from ride Hz alone, `g/(2π·Hz)²`, plotted against vertical load factor with a bottom-out marker where sag crosses the entered ride height). Uncalibrated heuristic — see [PHYSICS.md](PHYSICS.md) Calibration notes and [KNOWN_ISSUES.md](KNOWN_ISSUES.md) | None directly — feeds `ch.cgHeight` |
| <!--@range fe.targetSpeed-->Target Speed | 60–200 mph | Flat Ride phase-cancelling speed target. The range is **not** the slider's own `min`/`max` — the control is displayed inverted (`value={240-fe.targetSpeed}`, so its 40–180 domain maps to 200–60 mph, OFF on the left) and `sanitizeTune` clamps the stored field to 60–200. This row read 40–180 until an audit caught it quoting the inverted domain as if it were mph. 200 is flat-ride OFF. Should scale with Ride Stiffness — the flat-ride rear/front ratio only stays inside the ~10–20% practitioner band up to ~2.0 Hz at the default 70 mph; stiffer setups need a higher Target Speed to stay in range. The app shows an amber advisory when the ratio exceeds ×1.25 — see [PHYSICS.md](PHYSICS.md#rearsecondary-hz-modes). Paired with Damping Balance Mode TIME SYNC it is the lowest-pitch combination in the model (glossary entry FLAT RIDE + TIME SYNC, `flat-ride-time-sync`; the alternatives checked are in [KNOWN_ISSUES.md](KNOWN_ISSUES.md)) | None directly |
| Diff Type | Race/Sport/Rally/Offroad/Drift | The fitted diff's lock curve (`DIFF_TYPE_SCALE`, effective lock per %). AUTO divides by it, so a gentler type gets more % for the same effect; the balance reads % × scale — see [FORMULAS.md](FORMULAS.md) | None in AUTO (same effective lock); in MANUAL the same % counts for less on a gentler type |
| EXIT (grouped under FRONT AXLE for FWD, REAR AXLE for RWD/AWD) | −50..+50, GRIP↔ROTATE | Accel-lock intent (sign-flipped for FWD so right always leans OS) — same GRIP/ROTATE vocabulary across all layouts. Stored `dr.diffBiasExit` positive = more accel lock on the driven axle, so it reads ROTATE on RWD/AWD and GRIP on FWD — see [PRESETS.md](PRESETS.md)'s column notes for stored vs displayed | Right = OVERSTEER-leaning |
| ENTRY (not SPORT, same axle group as EXIT) | −50..+50, STABLE↔LOOSE | Decel-lock intent. Stored `dr.diffBiasEntry` positive = more decel lock = STABLE on **every** layout; the slider is an unconditional negation (`value={-(dr.diffBiasEntry??0)}`) to land right = LOOSE, so the stored sign is the opposite of the reading here — see [PRESETS.md](PRESETS.md) | Right = OVERSTEER-leaning |
| EXIT — FRONT AXLE (AWD only) | −50..+50, PUSH↔NEUTRAL | Front-axle accel lock (independent of the FRONT/REAR AXLE EXIT above, which is rear-axle for AWD) | Left (PUSH) = more UNDERSTEER |
| POWER SPLIT (AWD, grouped under CENTER) | −30..+40 (20–90% rear) | Center torque split | Right (REAR) = OVERSTEER |
| <!--@range dr.brakeBiasShift-->Brake Bias (BRAKES) | −10..+10 points | Shifts the brake bias centre: `recBrakeBias`, or at PRO with Centre GRIP `gripBrakeBias`; the readout is the resulting % front, kept within 40–68 (`BRAKE_BIAS_MIN`/`MAX`). Stored `dr.brakeBiasShift` positive = rearward = ROTATE, matching the slider. Ignored in BEG, which has no BRAKES section | Right (ROTATE) = OVERSTEER-leaning on entry |
| <!--@range dr.brakeDecel-->Decel (BRAKES, PRO, Centre GRIP) | 0.30..1.50 g, step 0.05 | The braking load GRIP's brake bias is solved at (`gripBrakeBiasOf`). Default 1.0 g, threshold braking. Shown only with Centre GRIP; INT reads Centre as REC | Right = GRIP moves forward = steadier entry |
| <!--@range dr.brakeEntryTarget-->Entry vs MID (BRAKES, PRO, Centre ENTRY) | −5..+5 %, step 0.25 | The ENTRY BRK target `entryBrakeBiasFor` solves the brake bias for, in grip-margin percent; replaces the Brake Bias shift, which is hidden. About 0.45% per bias point, so 40–68 reaches roughly +7% to −5%; past that the bias stops at the end with a note | Right (+) = looser entry = OVERSTEER-leaning |

## Pro (PRO) — adds these

| Slider | Range | Effect | Balance Direction |
|---|---|---|---|
| Wheelbase | 400–4,000mm | Flat-ride Hz solve, brake balance | None directly |
| Track Width F/R | 1,000–2,600mm | Roll-stiffness lever arm; feeds natural mech balance | Wider front → understeer lean; wider rear → oversteer lean |
| Mech Balance Target (NATURAL) | delta from NAT, so the result lands in 0.05–0.95 (≈−0.50..+0.75), step 0.005 | Balance Target NATURAL. MECH/CO-SOLVE solve to `natDisplayOf(ch, gameMode) + delta` — the display-space natural, so 0 means display exactly NAT. Switching in from RANGE, GRIP or MANUAL resets the delta to 0, so the target lands on natural. (A fresh or reset tune still stores `null`, which resolves to `MECH_BALANCE_TARGET`.) Under MECH with AUTO stiffness the bar budget grows as far as the target needs, capped at the springs' roll stiffness ([PHYSICS.md](PHYSICS.md)). ROLL/SHARE/BASIC keep the budget you set, and a target beyond them raises the clamp warning, which names the limiting bar | Positive = OVERSTEER target, negative = UNDERSTEER target |
| DNA axes (DNA modal) | each axis's `DNA_AXES` range | Edit a DNA draft, not the tune. APPLY compiles it onto Ride Stiffness, Rear Multiplier, ARB Share, Balance Offset, Rebound ζ, Bump Ratio, Damping Bias, EXIT and ENTRY — see [DNA.md](DNA.md) | As the control each compiles onto |
| Balance Offset | −0.20..+0.20, step 0.005 | Balance Target RANGE and GRIP modes share it. RANGE: offset from the middle of the Balance Guide RANGE (`balanceBandOf`), which is built from that same grip-neutral. In the Forza modes both anchors are taken at the tune's own roll stiffness, so they move with springs and bar budget. Switching in from any other mode, RANGE↔GRIP included, resets the offset to 0, so the target lands on the new anchor | Positive = OVERSTEER, negative = UNDERSTEER |
| <!--@range fe.arbBalAbs-->Mech Balance Target (MANUAL) | 0.05–0.95, step 0.005, default 0.60 | Balance Target MANUAL: the raw mech balance to solve toward, as the game displays it. Switching in seeds it from the target the previous mode had resolved to, so the switch does not move the tune | Above 0.50 = rear roll stiffness bias (OVERSTEER), below = front (UNDERSTEER) |
| <!--@range ch.arbMotionRatioF-->ARB Motion Ratio F / R (BEAMNG only) | 0.20–1.50, default 1.00 | Anti-roll bar arm as a fraction of track — where the drop link attaches. Separate from Motion Ratio F/R: spring mount and drop link are independent geometry. 1.0 assumes the bar acts at the wheels, which reads ~4–6× soft; a typical inboard link is ~0.4–0.5 | None — display and entry only, the solve never reads it |
| Motion Ratio F / R (BEAMNG only) | 0.20–1.50, default 1.00 | Spring/damper travel per unit wheel travel. Divides the *displayed* spring and damper rate by `mr²`, because BeamNG's sliders act at the spring while the solver works in wheel rate. Hidden in the Forza modes, which display wheel rate already. | <!--@range fe.springShare-->Spring Share (CO-SOLVE) | 0–100% | Splits correction between spring Hz and ARB split. | Accel/Decel Lock (MANUAL diff) | 0–100% each | Direct per-axle lock % | Accel lock: rear → OVERSTEER, front → UNDERSTEER. Decel lock on either axle → UNDERSTEER (resists lift-off rotation; less decel lock = more rotation on entry) — see [FORMULAS.md](FORMULAS.md) |
| Center Split (MANUAL AWD) | 0–100% rear | Direct torque split | Higher % rear → OVERSTEER |
| Nudge Strength (Alignment AUTO, Nudge MECH/GRIP) | 0–100%, default 50% | Scales how far camber/toe are nudged from the AUTO values toward the MECH/GRIP gap (see [ALIGNMENT.md](ALIGNMENT.md)). Shown only while Nudge is MECH or GRIP | 0% = no nudge (identical to AUTO with Nudge OFF); direction comes from the gap's sign, not this slider |
| Camber F/R, Toe F/R, Caster (Alignment MANUAL) | Camber −4.0/−3.5..0.0°, Toe −0.20..0.15° / 0.0..0.25°, Caster 4.0–7.5° | Direct entry, bypasses `computeAlignment` entirely | None directly — whatever you type |

## Auto-computed by default, or PRO's Alignment Mode

BRAKES (balance % — pressure was removed as dead output) is computed from build type/
layout/weight bias/chassis geometry, and from INT adjustable through the BRAKES section (see
the Brake Bias rows above); the recommendation and every adjusted bias are clamped to
**40–68% front**. Values below 50 (a rear bias, valid for trail-braking and
drift) are reachable only for rear-weighted cars on DRIFT/DRAG builds — the
CG/wheelbase weight-transfer term front-biases everything else. ALIGNMENT
(camber, toe, caster) is computed the same way by default (AUTO, stored as
`al.mode:'build'`), but PRO mode adds an Alignment Mode toggle — AUTO / MANUAL,
with a Nudge OFF / MECH / GRIP row under AUTO — see the
Nudge Strength/Camber/Toe/Caster rows above and
[ALIGNMENT.md](ALIGNMENT.md) for the full reference.
